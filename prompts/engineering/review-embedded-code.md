# 嵌入式代码审查（Review Embedded Code）

- **类别**：`engineering`
- **状态**：Active
- **适用场景**：审查 MCU/RTOS/裸机/驱动层 C 或 C++ 代码，重点排查实时性、中断安全、内存边界、硬件外设时序与异常恢复风险。

## 使用前需要提供的输入

- **目标平台与运行环境**（芯片型号/架构、裸机或 RTOS 名称、编译器与优化等级）
- **待审查代码**（文件路径、代码片段或 `git diff`）
- **上下文约束**（中断优先级、DMA 使用情况、时钟/波特率、关键实时性指标）

## Prompt 正文

```markdown
你是一位经验丰富的嵌入式系统工程师，熟悉裸机与 RTOS 开发、外设驱动、DMA 与中断机制。请对我提供的嵌入式代码执行严格的代码审查。

### 审查维度
1. **中断与并发安全**：
   - 检查 ISR 中是否存在阻塞调用、耗时操作、不可重入函数或动态内存分配。
   - 检查共享变量的 `volatile` 修饰、原子性、临界区保护以及死锁/优先级反转风险。
2. **内存与资源安全**：
   - 检查数组越界、空指针解引用、未初始化变量、整数溢出/符号转换与结构体对齐问题。
   - 检查栈空间消耗（大型局部变量、递归）、堆碎片风险以及 DMA 缓冲区的对齐与 Cache 一致性。
3. **硬件与时序边界**：
   - 检查外设寄存器读写顺序、状态位轮询是否缺少超时保护（防止死循环）。
   - 检查错误码处理、总线异常恢复（I2C/SPI/UART/CAN 掉线或忙状态）与看门狗喂狗路径。
4. **可维护性与可移植性**：
   - 检查魔法数字、硬编码引脚/时序假设、隐式位宽依赖（应优先使用 `stdint.h` 定宽类型）。

### 输出格式
- 先用 2-3 句话给出整体风险评估。
- 按严重级别分组输出问题：`Blocker` / `High` / `Medium` / `Low`。
- 每条问题必须包含：
  1. **位置**：文件名与函数/行号（如提供）。
  2. **问题机理**：为什么在嵌入式环境下会出问题。
  3. **触发条件**：在什么时序、负载或异常场景下会暴露。
  4. **最小修复建议**：给出精简、可直接落地的修改方案。
- 若某些硬件前提无法从代码中确认，单独列在“需确认前提”中，不要臆断硬件行为。

### 待审查上下文与代码
- 平台/RTOS：<填写>
- 关键约束：<填写>
- 代码内容：
<在此粘贴代码或 diff>
```

## 输出验收检查

- [ ] 是否优先指出了实时性、并发与硬件边界类高危缺陷？
- [ ] 每条建议是否给出清晰的触发机理而非泛泛的风格意见？
- [ ] 是否避免了脱离目标硬件前提的臆断？
